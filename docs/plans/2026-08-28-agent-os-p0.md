# ContextOS Agent OS P0 Implementation Plan

## Goal

Close the two verified runtime gaps before introducing the durable Agent OS runtime:

1. The Skills route must not crash when SkillHub returns an object-valued author.
2. MCP agent templates must create a project whose prompt, default skill, model, and tool dependencies are actually consumed by the chat runtime.

## Global Constraints

- Work only on branch `codex/agent-os-p0` in the isolated worktree.
- Use test-first development and record the failing and passing commands.
- Preserve the current project/chat experience and existing IndexedDB data.
- Do not add the SQLite Agent OS runtime in P0.
- Do not push, merge, publish, install system services, or change external state.
- Do not store or expose real credentials.
- Keep one canonical runtime contract for project agent configuration; do not add a second UI-only representation.

## Task 1: SkillHub boundary hardening

### Behavior

- Normalize `author` to a display-safe string when the API returns a string, object, missing value, or malformed value.
- Preserve the author object as structured metadata only if useful; React rendering must receive a string.
- Add a route-level error boundary so a future malformed remote card cannot blank the whole application.
- The Skills page must render built-in content even when remote results are malformed or unavailable.

### Tests

- A normalization test using the observed `{ name, logoUrl, verified, certifiedName, orgId }` author shape fails before the fix and passes after it.
- Missing and string-valued authors retain stable fallback behavior.
- A component test proves the Skills page renders a remote skill with object-valued author without throwing.
- An error-boundary test proves a child render failure produces a recovery screen rather than a blank root.

### Likely ownership

- `src/lib/skillhub.js`
- `src/pages/SkillsPage.jsx`
- `src/App.jsx`
- one small error-boundary component
- test configuration and Task 1 tests

## Task 2: Agent template runtime contract

### Behavior

- Introduce one project agent configuration shape containing template ID, system prompt, default skill ID, required MCP server IDs, and model capability requirements.
- MCP template deployment writes that configuration and binds the installed template skill as the project default.
- ProjectChat consumes the project-level system prompt when no thread-specific override or explicitly bound skill overrides it.
- Required MCP dependencies are visible in project runtime state. Missing dependencies must not be silently presented as a fully deployed agent.
- Keep current risky-tool approvals unchanged.
- Keep non-Claude model behavior honest: models without tool capability may chat, but the UI/runtime must not claim the agent can execute MCP tools.

### Tests

- A project created from the research template contains the expected runtime configuration and active skill.
- The system-prompt resolver selects explicit active skill, thread override, project agent prompt, then generic default in documented precedence.
- Missing MCP dependencies produce a non-ready runtime status.
- A non-tool-capable model produces a non-ready tool status instead of a false-ready agent.

### Likely ownership

- `src/pages/MCPPage.jsx`
- `src/pages/ProjectChat.jsx`
- new small pure runtime-contract module under `src/lib/`
- Task 2 tests

## Task 3: P0 integrated verification

- Run the full test suite, lint, and production build.
- Start the local app and verify Overview, Skills, MCP, and a deployed template project in the browser.
- Confirm the original Skills white-screen reproduction no longer occurs.
- Confirm the created agent project exposes its effective prompt, skill, model readiness, and MCP readiness.
- Run an independent whole-branch review against this plan.
- Record any deferred P1 items without implementing the SQLite runtime.
